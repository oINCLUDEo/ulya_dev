# Работа над Ulya VPN (dev_vpn)

Практические правила для этого репозитория: ветки, коммиты, версионирование,
релизы. Здесь описано то, как мы реально работаем — не смахивает на
теоретический документ, который никто не соблюдает.

## Ветки

- `master` — то, что реально выпущено. Каждый коммит на ней — это релиз
  (см. [Релизы](#релизы)).
- `dev` — интеграционная ветка. Вся разработка фич сначала попадает сюда.
- Ветки фич — создаются от `dev`, называются `<type>/<short-slug>`
  (`feat/reserve-grace-ui`, `fix/servers-note-decoding`). Мержатся обратно в
  `dev` по готовности, потом удаляются.

В `master` не должно быть прямых коммитов вне цикла релиза.

## Коммиты

Формат (на английском — так уже 120+ коммитов в истории, менять язык самого
формата задним числом смысла нет): `type(scope): summary`, повелительное
наклонение, без точки в конце.

```
fix(servers): decode admin note text, don't hide real servers behind it
feat(vpn-tile): connect directly from the Quick Settings tile
```

**Типы** (они же превращаются в секции CHANGELOG.md — см. ниже):

| Тип        | Смысл                                          | Секция в changelog |
|------------|--------------------------------------------------|---------------------|
| `feat`     | Новая функциональность, видимая пользователю      | Added               |
| `fix`      | Исправление бага                                  | Fixed               |
| `refactor` | Внутреннее изменение, поведение не меняется        | (не попадает)       |
| `style`    | Визуал/копирайтинг, без изменения логики          | Changed             |
| `chore`    | Тулинг, зависимости, CI, конфиг сборки            | (не попадает)       |
| `docs`     | Только документация                               | (не попадает)       |
| `test`     | Только тесты                                      | (не попадает)       |

**Scope** — страница/сервис/фича, к которой относится изменение (`servers`,
`premium`, `vpn-tile`, `subscription`, `onboarding`, ...) — как уже сложилось
в истории, продолжаем так же.

Один коммит может объединять несколько небольших связанных изменений под
одним `feat`/`fix`, если они прилетают вместе как один осмысленный кусок
работы (в этом репо так уже принято — например, пачка связанной визуальной
полировки одного экрана одним коммитом). Не нужно насильно делать коммит на
каждый файл, если изменения имеют смысл только вместе. А вот когда изменения
реально не связаны — разделяйте (багфикс + не связанная с ним новая фича —
это два коммита, два абзаца в changelog).

Тело коммита (опционально, через пустую строку после заголовка): объясняет
*почему*, а не что — что именно изменилось и так видно из диффа.

## Версионирование

Единственный источник правды — `version: MAJOR.MINOR.PATCH+BUILD` в
`pubspec.yaml`. SemVer для трёх чисел через точку, монотонный номер сборки
для четвёртого:

- **MAJOR** — breaking-изменение: миграция данных, из которой нельзя
  откатиться, редизайн, меняющий базовую навигацию/сценарии, отказ от
  поддержки версии платформы.
- **MINOR** — новая функциональность, видимая пользователю, обратно
  совместимая (новая страница, новый тип карточки, новая настройка).
  Поднимаем для типичной `feat`-работы.
- **PATCH** — только багфиксы и полировка, ничего, что тянет на пункт в
  описании новой фичи. Поднимаем для релизов из `fix`/`style`.
- **BUILD** (`+N`) — увеличивается на *каждой* сборке, которая покидает вашу
  машину (внутренний тест-билд, отправка в стор — неважно). Никогда не
  сбрасывается, не переиспользуется, живёт независимо от бампа
  MAJOR.MINOR.PATCH.

Что бампать (MAJOR/MINOR/PATCH) — решается по накопленным коммитам с
последнего релизного тега: если был хоть один `feat` — минимум MINOR; если
только `fix`/`style`/`refactor`/`chore` — PATCH; MAJOR — осознанное решение,
не автоматика.

## Релизы

Релиз — это: поднять версию, записать changelog, смержить `dev` в `master`,
поставить тег.

1. В `dev` решить новый номер версии (см. выше) и обновить `pubspec.yaml`.
2. Перенести всё содержимое `[Unreleased]` в `CHANGELOG.md` в новую секцию
   `[MAJOR.MINOR.PATCH] - YYYY-MM-DD` (точный формат — см. заголовок самого
   `CHANGELOG.md`). `[Unreleased]` оставить пустой для следующего цикла.
3. Закоммитить как `chore(release): vMAJOR.MINOR.PATCH`.
4. Смержить `dev` → `master` (fast-forward или merge-коммит, не squash —
   отдельные коммиты как раз и есть материал, из которого собирался
   changelog).
5. Поставить тег на этот коммит в `master`: `git tag vMAJOR.MINOR.PATCH`.
6. Запушить `master` и тег.
7. Собрать релизный артефакт (`flutter build apk --release` /
   `flutter build appbundle`) именно с этого закоммиченного тега.

Пока этот процесс не внедрён, `master` отстаёт от `dev` на 120 коммитов, тегов
нет, а `pubspec.yaml` до сих пор на дефолте от `flutter create`
(`1.0.0+1`) — следующий релиз-кат — подходящий момент выбрать реальный
стартовый номер (с учётом накопленного `feat`-объёма с последнего
неформального "v1.1.0" — это минимум MINOR-бамп от него, то есть `1.2.0`) и
начать ставить теги с этой точки.
